# BitMan 수익성 연구 핵심: 구현과 검증

작성일: 2026-10-14 KST. 상태: 격리 연구 모듈 구현·검증 완료. 운영 연결·수익성 실증은 미완료.

사용자의 “스스로 진화하고 수익을 낼 수 있는 시스템” 요청을 기존 재설계 A단계의 구현 진행으로 받아들였다. 목표는 실제 데이터를 기준으로 조건을 계산하고, 미래 성과를 평가하며, 같은 입력의 기존/개선 버전을 비교하는 실행 가능한 기반이다. 새로운 전략의 수익성이나 실제 거래 수익을 입증했다는 뜻은 아니다.

## 구현

| 모듈 | 실제 동작 |
|---|---|
| `ResearchConditionEngine` | 지표·단위·종목·시각·충돌 검사, 참/거짓/미확인, 검색 순서, 고유 후보·부분 범위·결정론 순위 |
| `PublicPickSnapshotAdapter` | 기존 공개 저장본만 읽고 허용된 수치·출처를 추출. 수집 가능 시각을 최초 반입 시각으로 기록하고 이전 시세와 혼동하지 않음 |
| `ResearchOutcomeEvaluator` | KRX 정규장 종가 이후 신호의 다음 세션 시가 참조·1/3/5/20세션 종가 변화. 비용/비교 대상 미확인은 null, 정지·누락·기업행동·경로 모호성을 구분 |
| `ResearchRunStore` | 회원 저장소와 별도 H2 연구 원장. 동일 입력 재사용, 취소·늦은 저장·만료 lease 검사, 불명확한 비용 예약 보존 |
| `ResearchLearningService` | 같은 날짜·종목·평가/비용/입력 버전의 기준/개선안 비교. 손실·누락·중복·중첩 기간을 포함하고 검토 후보만 제안 |
| `ResearchCoreCli` | 실제 공개 저장본 → 조건 검사 → 미측정 사유 → 비교 학습 → 영속 결과 → JSON/한국어 보고서를 끝까지 실행 |

신규 클래스는 Spring 서비스로 등록하지 않는다. 자동 주문·운영 스케줄·회원 DB·Telegram·유료 모델 호출을 만들지 않는다. 사용자가 명시적으로 실행하는 `researchCore` Gradle 작업을 제공한다.

## 실행

Git Bash에서 현재 체크아웃의 JDK 21을 사용한다.

```bash
PROJECT="/c/bitman_justbuy_project"
PYTHON="$PROJECT/.venv/Scripts/python.exe"
FRONTEND="$PROJECT/frontend"
cd "$PROJECT"
JAVA_HOME="/c/Program Files/Microsoft/jdk-21.0.10.7-hotspot" ./backend/gradlew -p backend researchCore
```

출력은 `backend/build/research-core/report.json`, `report.md`와 별도 `research-ledger/`다. 새 연구 작업 공간을 쓰려면 `-PresearchWorkspace=build/another-research-core`를 지정한다. 기존 공유 폴더·회원 DB를 작업 공간으로 사용하면 거부한다.

현재 CLI의 대표 조건은 **저장 목표/손절 가격 거리 비율 ≥1**이다. 이 비율은 기대수익이나 추천 점수가 아니다. 실제 과거 픽의 상태를 재현하는 작은 조건이며 PER·수급·기술 조건을 지원하는 순수 엔진과 미래 관측 평가기를 독립적으로 검사한다. 다른 지표가 없는 공개 저장본에서 값을 생성하지 않는다.

## 실제 입력 결과

`docs/DETECTED_STOCK_QUALITY_SNAPSHOT_2026_10_12.json`을 새 코드로 읽었다.

- 표시 9건, 서로 다른 종목 4개, 가격 거리 비율 1 미만 4건.
- 당시 시세는 현재 30분 유효성 정책에서 오래된 자료다. 조건 판정은 미확인이고 현재 추천으로 통과하지 않는다.
- 전체 시장 분모와 영구 종목 마스터가 없어 부분 범위다.
- 이 저장본에는 실제 공개 시각·거래소/세션·미래 봉의 완전한 계약이 없어 4개 종목의 성과는 미측정이다.
- 실제 완료 미래 성과 0건, 비교 가능한 실측 학습 표본 0건, `INSUFFICIENT_EVIDENCE`.
- 개선 검토가 좋아 보여도 `productionActivationAllowed=false`다. 연구 검토 후보는 수익성 입증이나 운영 자동 승격이 아니다.

실제 출력의 공개 복사본은 이 문서 옆 `2026-10-14-profit-core-public-report.json`에 둔다. 테스트의 정상/수익/손실/정지/분할/경로 사례는 명시적으로 구성한 예외 자료이며 실제 주식 성과로 세지 않았다.

## 의미 있는 검증

테스트를 먼저 실패시킨 뒤 구현·수정했다. 독립 리뷰에서 다음 오류를 재현해 보완했다.

1. 음수 PER 자격 제외가 순위 먼저/조건 나중 의미를 바꾸던 경계.
2. 같은 값이라도 공급자·REAL/MOCK 환경이 다를 때 반입 어댑터가 차이를 지우던 경계.
3. 20세션 평가를 당일 종료로 입력해 독립 날짜를 부풀리던 경계.
4. 장 시작 전 공개 신호를 다음 날짜 시가에 자동 적용하던 경계. 첫 정책은 종가 이후 전용으로 고정.
5. 옛 실행이 늦게 끝나 최신 보고서를 덮는 경계. 실행별 결과를 보존하고 프로세스/파일 잠금과 cutoff 검사로 공유 보고서를 보호.

원장 검사는 실제 임시 H2 파일·닫기/재열기·동시 핸들·취소·lease 만료를 사용했다. Windows junction 경계 검사는 통과했다. Windows symbolic link 생성은 권한에 따라 한 검사에서 건너뛰며 이 한계를 숨기지 않는다.

최종 정상 Gradle 명령 `test bootJar`는 113개 클래스/1,053개 검사, 실패·오류 0건, 1건 건너뜀으로 통과했다(1,052개 실행 성공). 신규 모듈은 109개 중 108개 성공/1개 권한 건너뜀이다. 기존 Spring Boot 실행 클래스가 선택된 생산 JAR 빌드도 통과했다. 수정된 프론트엔드가 없어 frontend 검사·브라우저 배포 검증은 수행하지 않았다.

최종 `researchCore` 실제 실행은 `savedSlots=9`, `uniqueStocks=4`, `measuredOutcomes=0`, `profitabilityStatus=INSUFFICIENT_EVIDENCE`, `productionActivationAllowed=false`로 종료했다. 동일 동결 입력의 재열기 재사용과 시각/입력 변경의 무효화는 실제 H2 회귀 검사로 확인했다. 운영 MiniPC·Pages·스케줄·회원 DB·키는 변경하지 않았다.

## 구현 범위의 한계

- 새 조건 엔진은 `COMPLETE`와 `KNOWN_SUBSET`을 구분한다. 증명하지 않은 `TOP_K_PROVEN`은 반환하지 않는다.
- 공급자별 REAL/MOCK 자료는 각각 허용하지만 서로 다른 근거를 하나로 평균내지 않는다. 복수 원천 충돌은 추가 원천 선택 정책이 있어야 해소할 수 있다.
- 성과 계산기는 호출자가 제공한 검증된 KRX 캘린더를 사용한다. 정규장 종료 15:30 정책만 지원하며 다른 거래소·시간외·장중 진입은 별도 정책이다.
- 가격 변화/시나리오는 실제 체결이 아니다. 비용은 명시적 가정이며 호가·부분 체결·실제 계좌의 수수료를 확인하지 않았다.
- 학습기의 최소 날짜 간격은 불가능한 기간을 거부하는 필요조건이다. 거래 달력·원천 관측 자체를 인증하지 않는다. 기본 30개 비중첩 날짜도 통계적 충분성·수익 보장이 아니다.
- 근거·실행 저장은 이 모듈의 재현 기반이다. 공급자 API 연결·실제 이후 봉 자동 수집·관리자 UI·생산 알림·배포는 B/C 단계다.
- 자동 모델 가중치 변경 또는 AI 모델 자체의 진화를 구현했다고 주장하지 않는다. 검증된 결과를 바탕으로 변경 후보를 비교하는 절차를 만든 것이다.

## 다음 실증

유료 회원 앱·Telegram 제공, 자료 저장·AI 입력에 대한 KIS/키움 정보 이용 범위는 여전히 사용자 확인이 필요하다. 이번 오프라인 모듈은 새 키나 유료 모델 설정을 요구하지 않는다.
